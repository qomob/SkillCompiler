# Meta-Reflection — 编译过程自省框架

**加载时机：** 在各 Pass 的 Decision Gate 处按需引用。编译器在执行关键决策后，用此框架对自己的判断进行二次审视。

---

## 设计哲学

编译 Skill 不仅是机械的"输入→分析→设计→生成"。编译器在高模糊性的决策点（如"这个能力是 primary 还是 secondary？""这个架构选 workflow 还是 multi-agent？"）容易陷入经验惯性或盲区。

**元反思是编译器的"自我审计"机制**——在关键决策后，暂停片刻，用结构化维度审视刚才的判断是否经得起推敲。

---

## 八维度框架

| # | 维度 | 核心问题 | 适用阶段 |
|---|------|---------|---------|
| D1 | **问题定义** | 我是否理解了真正的问题？有没有更好的问题表述？ | Pass 1 Analysis |
| D2 | **假设** | 我的关键假设是什么？哪些未经验证？ | Pass 1 Analysis |
| D3 | **推理** | 推理链是否存在跳跃、循环或逻辑漏洞？ | Pass 3 Design |
| D4 | **证据** | 哪些观点有证据支持？哪些只是推测？ | Pass 2 Extract, Pass 6 Validate |
| D5 | **替代解释** | 是否存在其他同样合理甚至更好的解释？ | Pass 3 Design |
| D6 | **边界条件** | 结论适用于哪些场景？什么时候会失效？ | Pass 3 Design |
| D7 | **目标** | 当前优化目标是否正确？是否应该优化更高层目标？ | Pass 1 Analysis, Pass 6 Validate |
| D8 | **不确定性** | 我最没有把握的部分是什么？还需要哪些信息才能提高可信度？ | Pass 1 Analysis, Pass 6 Validate |

## 各维度详解

### D1 — 问题定义（Problem Definition）

**核心问题：** 我是否理解了真正的问题？有没有更好的问题表述？

**在编译上下文中的含义：**
- 用户给的 Prompt 字面含义 vs 真实需求是否一致？
- `prompt_goal.stated` 和 `prompt_goal.actual` 的差距有多大？
- 有没有更精确的方式描述这个 Skill 要解决的问题？

**触发时刻：** Pass 1 Step 1.2 Goal Extraction 完成后

**自检清单：**
- [ ] stated goal 是否只是 actual goal 的表面表述？
- [ ] 如果换一种方式定义这个问题，skill 的设计会完全改变吗？
- [ ] 用户可能没有说出来的深层需求是什么？

---

### D2 — 假设（Assumptions）

**核心问题：** 我的关键假设是什么？哪些未经验证？

**在编译上下文中的含义：**
- `hidden_assumptions` 列表中的每一项——有没有办法在编译过程中验证而非假设？
- 假设用户"熟悉 Skill 结构"是否导致跳过了必要的解释？
- 假设"输入格式稳定"是否忽略了格式退化场景？

**触发时刻：** Pass 1 Step 1.6 Hidden Assumptions 完成后

**自检清单：**
- [ ] 每个 hidden_assumption 是否标注了"可验证"还是"不可在编译期内验证"？
- [ ] 是否存在"假设用户会正确使用"这一隐含假设？
- [ ] 最脆弱的一个假设如果错了，哪些设计决策会崩塌？

---

### D3 — 推理（Reasoning）

**核心问题：** 推理链是否存在跳跃、循环或逻辑漏洞？

**在编译上下文中的含义：**
- architecture_type 的决策链是否有跳跃？("因为有多个步骤 → 所以选 workflow"——但步骤间是否需要不同专业角色？)
- workflow pattern 的选择是否自洽？(classify-and-act + pipeline 的组合是否合理？)
- 模块拆分的依据是否一致？(为什么规则 A 独立成文件而规则 B 内联？)

**触发时刻：** Pass 3 Step 3.1 Architecture Type 决策后、Step 3.4 Module Decomposition 后

**自检清单：**
- [ ] 每个"因为 X 所以 Y"的推理步骤是否可以回溯到明确的条件？
- [ ] 是否存在循环推理——"选 A 是因为 B，而 B 的定义来自 A"？
- [ ] 模块拆分标准是否前后一致？

---

### D4 — 证据（Evidence）

**核心问题：** 哪些观点有证据支持？哪些只是推测？

**在编译上下文中的含义：**
- 每条知识的 `evidence` 字段：primary / secondary / inferred 的分布是否健康？
- inferred 条目是否标注了推断依据？
- 是否存在大量 inferred 知识被当作 primary 使用？

**触发时刻：** Pass 2 Step 2.2 Knowledge Inventory 后、Pass 6 Layer B 验证时

**自检清单：**
- [ ] inferred 条目占比是否 > 30%？如果是，skill 的可信度是否足够？
- [ ] 是否存在"所有人都知道"但其实只是推断的知识？
- [ ] 冲突条目（conflicts）是否都有来源标注？

---

### D5 — 替代解释（Alternative Explanations）

**核心问题：** 是否存在其他同样合理甚至更好的解释？

**在编译上下文中的含义：**
- 能力图谱的 primary/secondary 划分是否有替代方案？
- 架构类型的选择是否有同等级有力的替代方案？
- 当前选定的 workflow pattern 之外，是否存在另一个 pattern 同样合理？

**触发时刻：** Pass 3 Step 3.1-3.2 架构与 workflow 决策后

**自检清单：**
- [ ] 至少考虑过 1 个替代的 architecture_type 并给出淘汰理由
- [ ] 至少考虑过 1 个替代的 workflow pattern 并给出淘汰理由
- [ ] 替代方案的优势是否被诚实评估？（而非刻意贬低以证明当前选择正确）

---

### D6 — 边界条件（Boundary Conditions）

**核心问题：** 结论适用于哪些场景？什么时候会失效？

**在编译上下文中的含义：**
- boundary.out_of_scope 是否足够具体？还是泛泛的"不处理无关请求"？
- 当前设计的 architecture 在什么条件下会变成错误选择？
- 生成的 skill 在什么使用场景下会表现不佳？

**触发时刻：** Pass 3 Step 3.4-3.8 模块设计与目录规划后

**自检清单：**
- [ ] out_of_scope 条目是否都足够具体，可被 Pass 6 Layer C 的压力测试验证？
- [ ] 设计的架构在以下极端条件下是否仍适用：输入为空 / 输入极长 / 输入格式退化？
- [ ] skill 的失效模式是否在 honest-boundaries 中声明？

---

### D7 — 目标（Goals）

**核心问题：** 当前优化目标是否正确？是否应该优化更高层目标？

**在编译上下文中的含义：**
- 当前在优化"Prompt 长度"还是"Skill 可维护性"——这两个目标冲突时优先级是什么？
- 是不是在过度优化某个指标而牺牲了更重要的指标？
- 编译的最终目标是"产出高质量 skill"还是"通过所有 Pass"？

**触发时刻：** Pass 1 完成后、Pass 6 综合评分前

**自检清单：**
- [ ] "降低 token 消耗"是否导致关键知识被移除？
- [ ] "提高评分"是否导致过度设计——加了不必要但能加分的模块？
- [ ] 最终产出对用户而言真的可用吗？（而非只是在 IR 中看起来好）

---

### D8 — 不确定性（Uncertainty）

**核心问题：** 我最没有把握的部分是什么？还需要哪些信息才能提高可信度？

**在编译上下文中的含义：**
- unknowns 列表中是否遗漏了关键的不确定信息？
- 编译过程中哪些决策是"猜测"而非"推理"？
- 哪些推断如果能向用户确认，会显著提高 skill 质量？

**触发时刻：** Pass 1 Step 1.7 Unknowns 后、Pass 6 最终审查时

**自检清单：**
- [ ] 是否有超过 3 个未被询问的 unknowns？（如果是，选最重要的 3 个问用户）
- [ ] 最终的 skill 中哪些部分是"我们猜的"而非"确定的"？
- [ ] 如果只能向用户确认一件事来提高 skill 质量，那件事是什么？

## 使用约束

1. **每个检查点不超过 3 个维度**——不是所有维度都要在每处应用
2. **只问能改变决策的问题**——如果某个维度的回答不会改变任何设计，跳过它
3. **记录但不阻塞**——meta-reflection 的输出写入 trace 或日志，但不应成为 Decision Gate 的硬阻塞条件。它是编译器自我校准的机制，而非额外的审批门槛
4. **快速模式跳过**——compilation_mode 为 `quick` 时，meta-reflection 检查点全部跳过（token 成本优先）
